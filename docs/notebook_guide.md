500 SQuAD v2 test questions (250 answerable, 250 unanswerable), seed 42, identical prompt and scorer for all rows.

|---|---|---|---|---|---|

# Part 1 — Notebook walkthrough

Edit the builder, then run `python notebooks/build_simple_notebook.py` — never hand-edit the `.ipynb`.

```
Step 0 Setup → 1 Config → 2 Data split → 3 Prompt + masking → 4 Metrics → 5 Evaluate()

```

### Step 0 — Setup

**What it does:** installs the libraries Colab lacks and picks the device.

**Key terms**
- **CUDA / GPU** — NVIDIA's GPU runtime; training is only practical on a GPU.
- **PEFT** — Hugging Face library that implements LoRA.
- **bitsandbytes** — library that loads models in 4-bit/8-bit (needed for the 7B).

**Key code**
```python
subprocess.check_call([... 'pip', 'install', '-q', 'peft', 'bitsandbytes', 'torchao>=0.16.0'])
os.environ['HF_HUB_DISABLE_XET'] = '1'
DEVICE = 'cuda' if torch.cuda.is_available() else 'cpu'
```

**Why it is written this way**
- `torchao>=0.16.0`: Colab ships torchao 0.10, and recent `peft` refuses to import with anything older than 0.16.
- `HF_HUB_DISABLE_XET=1`: the Hub's newer "Xet" download path stalled on Colab and filled system RAM
  while downloading the 15 GB 7B model. Plain HTTP is fast and light.

### Step 1 — Config

**What it does:** one place for every setting.

| Setting | Value | Meaning |
|---|---|---|
| `DRY_RUN` | `True` / `False` | `True` = 64/16/16 examples, 1 epoch (~5 min smoke check). `False` = real run |
| `RUN_LLM` | `True` | run Setup 3 (the 7B baseline) |
| `SEED` | 42 | fixes every random choice → same test questions for all three models |
| `SLM`, `LLM` | Qwen1.5-0.5B, Qwen1.5-7B | **base** variants of the same family |
| `N_TRAIN/N_VAL/N_TEST` | 5000 / 500 / 500 | train / validation / test sizes |
| `EPOCHS` | 3 | full passes over the training set |
| `MAX_LEN` | 384 | max tokens per training example (prompt + answer) |
| `BATCH, GRAD_ACC` | 4, 4 | 4 examples per step, weights updated every 4 steps → effective batch 16 |
| `LORA` | r=8, alpha=16, dropout=0.05, q_proj+v_proj | adapter size and placement |

**Key terms**
- **Seed** — a number that makes "random" choices repeatable.
- **Epoch** — one pass over all training data.
- **Gradient accumulation** — sum gradients over several small batches before one update; gives a large
  effective batch without the memory cost.
- **Base vs instruct** — an instruct model has extra instruction-following training. Using base models for
  all three setups means any gain is attributable to LoRA alone.

### Step 2 — Data split

**What it does:** loads SQuAD v2 and builds disjoint train / validation / test sets.

**Key code**
```python
idx = np.random.default_rng(SEED).choice(len(squad['validation']), N_VAL + N_TEST, replace=False)
val_idx, test_idx = sorted(idx[:N_VAL]), sorted(idx[N_VAL:])
assert not set(val_idx) & set(test_idx), 'val/test overlap!'
train_idx = np.random.default_rng(SEED).choice(len(squad['train']), N_TRAIN, replace=False)
json.dump({'seed': SEED, 'test_indices': test_idx}, open(f'{OUT}/test_indices.json', 'w'))
```

**Key terms**
- **SQuAD v2** — reading-comprehension QA: a Wikipedia paragraph, a question, and a short answer span —
  or no answer at all (about half the questions are deliberately unanswerable).
- **Train / validation / test** — learn from / pick the best checkpoint with / report the final score on.
- **Data leakage** — a test question seen during training; it would make results meaningless.

**Why it is written this way**
- SQuAD v2 has no public labelled test split, so validation **and** test are taken from the HF
  `validation` split **in one draw** of 1,000 distinct indices, then cut 500 / 500. They cannot overlap,
  and the `assert` proves it at runtime.
- Training examples come from the HF `train` split, so they never overlap with val/test either.
- Validation/test use their own RNG, so the test set does not depend on `N_TRAIN`.
- Test indices are saved to `test_indices.json` so the exact test set can be audited.
- Result in the full run: 250 answerable + 250 unanswerable test questions.

---

### Step 3 — Prompt + masking

**What it does:** formats each example as text, converts it to token IDs, and marks which tokens are trained.

**Prompt format**
```
### Context:
<paragraph>

### Question:
<question>

### Answer:
<answer or "unanswerable"><eos>
```

**Key code**
```python
p = tok(prompt(ex))['input_ids']
a = tok(answer(ex) + tok.eos_token, add_special_tokens=False)['input_ids']
return {'input_ids': p + a, 'attention_mask': [1] * (len(p) + len(a)),
        'labels': [-100] * len(p) + a}
...filter(lambda e: len(e['input_ids']) <= MAX_LEN)
```

**Key terms**
- **Tokenizer / tokens** — text split into sub-word pieces, each mapped to an integer ID.
- **Labels** — the target tokens the loss is computed against.
- **Prompt masking (`-100`)** — PyTorch's cross-entropy ignores label `-100`, so no loss comes from the prompt.
- **EOS token** — "end of sequence"; teaches the model to stop after the answer.

**Why it is written this way**
- The model should learn to *produce the answer*, not to reproduce the paragraph — so only answer tokens
  carry loss.
- Prompt and answer are tokenized separately, so the mask boundary is exact.
- Over-long examples are **skipped**, not truncated: truncation could cut the answer off and leave a
  prompt-only example with nothing to learn. In the full run 4,926 / 5,000 training and 487 / 500
  validation examples were kept.
- The cell prints the trained tokens of one example as visible proof the mask is correct.

---

### Step 4 — Metrics

**What it does:** defines the scorer, and tests it.

**Key terms**
- **Normalisation** — lowercase, strip punctuation, remove *a/an/the*, collapse spaces (official SQuAD rules).
- **Exact Match (EM)** — 1 if the normalised prediction equals a normalised gold answer.
- **Token F1** — word overlap: precision = shared / predicted words, recall = shared / gold words,
  F1 = 2PR / (P + R). Gives partial credit.
- **Best-of-golds** — SQuAD has several valid gold answers per question; the best match counts.

**Why it is written this way**
- Scores are reported **overall, answerable-only and unanswerable-only**. About half the questions are
  unanswerable, so a model answering "unanswerable" every time would get ~50 % EM while understanding
  nothing. The split exposes that.
- A built-in self-check (`assert`) verifies the scorer on three hand-made cases before it is used.

---

### Step 5 — `evaluate()` and `log()`

**What it does:** the model *generates* an answer for every test question; answers are scored and timed.
`log()` appends a row to `results.csv` after every setup, so a later crash cannot lose earlier results.

**Key code**
```python
tokenizer.padding_side = 'left'
out = model.generate(**enc, max_new_tokens=32, do_sample=False, pad_token_id=tokenizer.pad_token_id)
preds.append(text.strip().split('\n')[0].strip())          # first line = the answer
scores['latency_ms'] = round(1000 * secs / len(examples), 1)
```

**Key terms**
- **Generation / inference** — running the model to produce text.
- **Greedy decoding** (`do_sample=False`) — always take the most likely next token → deterministic, repeatable.
- **Left padding** — in a batch, shorter prompts are padded on the left so every prompt ends exactly at
  `### Answer:` and generation starts in the right place.
- **Latency** — average generation time per question (GPU synchronised before and after timing).

**Why it is written this way**
- **All three setups go through this one function** — same prompt, same decoding, same scorer. This is
  what makes the comparison fair. (An earlier notebook scored the LoRA model with the Trainer's
  teacher-forced metric instead of generation, which made it incomparable to the baselines.)

---

### Step 6 — Setup 1: small model, zero-shot

**What it does:** loads Qwen1.5-0.5B and scores it with no training.

**Key terms**
- **Zero-shot** — the model performs the task with no task training and no examples in the prompt.
- **Baseline** — the reference point improvement is measured against.

**Why fp32:** the weights are loaded in float32; training later uses fp16 *mixed precision* (fp16 compute,
fp32 master weights), which is the numerically safe way to train on a T4.

**Result:** EM 5.6 · F1 16.39 · unanswerable EM 0.0. The base model answers in full sentences copied from
the paragraph and never says "unanswerable" — it was never taught this format.

---

### Step 7 — Setup 2: LoRA fine-tuning (the contribution)

**What it does:** freezes the 0.5B model, attaches LoRA adapters, trains them, saves the adapter and the
training log.

**Key code**
```python
model = get_peft_model(base, LoraConfig(task_type='CAUSAL_LM', r=8, lora_alpha=16,
                                        lora_dropout=0.05, target_modules=['q_proj', 'v_proj']))
args = TrainingArguments(..., learning_rate=2e-4, warmup_steps=10, lr_scheduler_type='cosine',
                         fp16=True, gradient_checkpointing=True,
                         eval_strategy='epoch', save_strategy='epoch', load_best_model_at_end=True,
                         prediction_loss_only=True, ...)
trainer.train()
model.save_pretrained(f'{OUT}/adapter')
```

**Key terms**
- **Fine-tuning** — further training a pre-trained model on a specific task.
- **PEFT** — parameter-efficient fine-tuning: train only a small number of parameters.
- **LoRA** — keep each weight matrix *W* frozen and learn a low-rank update *ΔW = B·A*
  (*A*: r × d, *B*: d × r). Output = *W·x + (α/r)·B·A·x*. *B* starts at zero, so training starts exactly
  from the base model.
- **Rank r = 8** — the inner size of *A* and *B*; controls adapter capacity and size.
- **α (lora_alpha) = 16** — scales the update (α/r = 2).
- **q_proj / v_proj** — the query and value projections inside self-attention, the standard LoRA targets.
- **Adapter** — the saved *A*, *B* matrices (a few MB); the base model is reused unchanged.
- **Loss** — cross-entropy on answer tokens; lower = better.
- **Learning rate 2e-4, warmup, cosine** — step size; ramp up over 10 steps, then decay smoothly.
- **Mixed precision (fp16)** — faster, less memory on a T4.
- **Gradient checkpointing** — recompute activations in the backward pass instead of storing them.

**Parameter count, from first principles:** Qwen1.5-0.5B has 24 layers, hidden size 1,024. Each LoRA
module adds r × (1,024 + 1,024) = 16,384 parameters; 2 modules × 24 layers = **786,432**, which is
**0.169 %** of 464,774,144.

**Why it is written this way**
- `prediction_loss_only=True` is **the fix for the earlier out-of-memory crashes**: with a metrics
  callback, the Trainer kept full-vocabulary logits for every validation token
  (~500 × seq × 152K values — tens of GB). Validation is now scored by loss only; real EM/F1 come from
  generation in Step 8.
- `load_best_model_at_end` keeps the epoch with the lowest **validation** loss — the test set is never
  used to choose anything.
- Only the adapter is saved — that is the practical benefit of PEFT.

**Result:** 924 optimisation steps, 21 min, peak 4,978 MB. Train loss 1.47 → 0.24; validation loss
0.417 → 0.399 → 0.393 (still improving at epoch 3).

**Result:** EM **68.8** · F1 **72.44** · answerable EM 66.4 · unanswerable EM 71.2 · 150 ms / answer.

### Step 9 — Setup 3: 7B zero-shot baseline

**What it does:** frees the small model's GPU memory, loads Qwen1.5-7B in 4-bit, scores it.

**Key terms**
- **Quantization** — store weights in fewer bits. 7B in fp16 ≈ 14 GB (too big for a 15 GB T4 with
  activations); in 4-bit ≈ 4–5 GB.
- **NF4** — "normal float 4", a 4-bit format designed for normally-distributed weights (from QLoRA).
- **Compute dtype fp16** — weights are de-quantised to fp16 for the matrix multiplies (T4 has no bf16).

**Why it is written this way:** same family and base variant as the SLM, so the only variable is size.
Batch size is 4 (vs 8 for the 0.5B) to fit memory.

**Result:** EM 27.8 · F1 36.55 · answerable EM 55.6 · unanswerable EM 0.0 · 1,139 ms / answer.

# Part 2 — Expected demo / viva questions

## A. Research question & design

**Q1. What is your research question?**
Can a small language model adapted with parameter-efficient fine-tuning (LoRA) reach competitive accuracy
on a document-analysis task while being much cheaper than a larger model? Phase 1 tests this on
extractive QA (SQuAD v2).

**Q2. Why three setups?**
Setup 1 vs 2 isolates the effect of LoRA. Setup 2 vs 3 asks how close a small tuned model gets to a
model 14× larger. Together they separate "fine-tuning" from "scale".

**Q3. How do you make the comparison fair?**
Same model family (Qwen1.5), base variants for all, the same 500 test questions (seed 42, indices saved),
the same prompt, greedy decoding, and the same `evaluate()` scorer for every row.

**Q4. Why base and not instruct models?**
Instruct models already have instruction tuning. Mixing variants would credit LoRA with gains that came
from someone else's instruction tuning.

**Q5. Why Qwen1.5?**
Open weights, no access token, a 0.5B size that trains on a free T4, and a 7B sibling with the same
tokenizer and architecture — so size is the only difference.

**Q6. Why SQuAD v2?**
It is a standard, text-native reading-comprehension benchmark with official metrics, and half its
questions are unanswerable — which tests whether a model knows when the document does not contain the
answer, an important property for document analysis.

## B. Data

**Q7. SQuAD v2 has no test set — how did you make one?**
One random draw of 1,000 distinct indices from the official validation split, cut into 500 validation and
500 test. They cannot overlap; an `assert` checks it and the test indices are saved for audit.

**Q8. Could test data leak into training?**
No. Training comes from the HF `train` split; validation/test come from `validation`, disjoint by
construction. Checkpoint selection uses validation loss only.

**Q9. Why skip long examples instead of truncating?**
Truncation could remove the answer and leave a prompt-only example. Only 74 of 5,000 training examples
exceeded 384 tokens.

## C. LoRA and training

**Q10. Explain LoRA in one minute.**
Freeze the pretrained weight *W*; learn a low-rank correction *B·A* added to it. With rank 8 on the
attention query and value projections we train 786K parameters — 0.169 % of the model. *B* starts at
zero, so training begins exactly at the base model, and only the small adapter is saved.

**Q11. Why rank 8 and q_proj / v_proj?**
These are the defaults from the LoRA paper's recommendations and give most of the benefit at the lowest
cost. Varying rank and target modules is planned ablation work.

**Q12. What is prompt masking and why?**
Prompt tokens get label −100 so the loss is computed only on the answer. The model learns to answer,
not to copy the paragraph.

**Q13. How do you know the model learned rather than memorised?**
Validation loss (on questions never trained on) fell every epoch: 0.417 → 0.399 → 0.393, and the test
set — also never seen — improved from 5.6 to 68.8 EM.

**Q14. Is it overfitting?**
Train loss (0.24) is below validation loss (0.39), which is normal, but validation loss was still
decreasing at epoch 3, so there is no sign of harmful overfitting. The best epoch by validation loss is
the one kept.

**Q15. What did training cost?**
21 minutes on a free Colab T4, 5.0 GB peak GPU memory, and a few-MB adapter.

**Q16. Why did earlier Colab runs run out of memory?**
The Trainer was given a metrics callback, which made it store full-vocabulary logits (~152K values per
token) for every validation token — tens of GB. Shrinking batch size could not fix that. The fix was
scoring validation by loss only (`prediction_loss_only=True`) and computing EM/F1 by generation afterwards.

## D. Evaluation

**Q17. What are EM and F1?**
EM: the normalised answer matches a gold answer exactly. F1: word-overlap harmonic mean of precision and
recall — partial credit.

**Q18. Why report answerable and unanswerable separately?**
Half the questions are unanswerable; always saying "unanswerable" would give ~50 % EM for free. Splitting
shows real reading ability (answerable EM) and real abstention ability (unanswerable EM).

**Q19. Why generation-based scoring instead of the Trainer's metrics?**
The Trainer's metric compares next-token guesses under teacher forcing, not answers the model would
actually produce. Generation is how the model is used, and it is identical for all three setups.

## E. Results

**Q20. What is the headline result?**
LoRA raised the 0.5B model from 5.6 to 68.8 EM (F1 16.4 → 72.4), and the tuned 0.5B model outscored the
zero-shot 7B (27.8 EM) while answering ~7.6× faster in our setup.

**Q21. Where does the improvement come from?**
Two places. (1) Format: the base model answers with full sentences; the tuned model gives short spans.
(2) Abstention: neither zero-shot model ever said "unanswerable" (0 of 500); the tuned model said it 222
times and was right 178 times (71.2 % of unanswerable questions).

**Q22. Isn't the 7B only losing because it never says "unanswerable"?**
Partly — that costs it the 250 unanswerable questions. On **answerable questions only**, LoRA still wins:
66.4 vs 55.6 EM. So the small tuned model is also better at extracting the right span, not only at
abstaining.

**Q23. Why is the LoRA model faster than the base model with the same size (150 vs 191 ms)?**
It generates short answers and stops (EOS); the base model rambles up to the 32-token limit. Generation
time is dominated by the number of tokens produced.

**Q24. Is "7.6× faster" a fair claim?**
Only "in our setup". The 7B ran in 4-bit (de-quantisation adds compute) and at batch 4 vs 8. The
direction is robust; the exact factor depends on precision, batch size and hardware.

**Q25. What mistakes does the LoRA model make?**
It over-abstains: 44 answerable questions were answered "unanswerable". It also sometimes gives a span on
an unanswerable question (e.g. "Byzantine Greece" where the gold is unanswerable). Full predictions are
in `experiments/simple/predictions.csv` for error analysis.

**Q26. Your earlier smoke test showed base EM = 20. Why is it 5.6 now?**
The smoke test is a pipeline check on a small sample (at most 25 test examples, drawn with different
split settings), so its number is noise. 5.6 is on the full 500-question test set, and it was identical
on Colab and on a local CPU run.

## F. Limitations & future work

**Q27. What are the limitations?**
- One run, one seed — report mean ± std over 2–3 seeds for the thesis.
- The 7B baseline is zero-shot with no instruction about "unanswerable"; a few-shot or instructed 7B
  would be a stronger baseline.
- SQuAD is clean Wikipedia text, not real business documents (no OCR noise, layout or tables).
- One task so far (QA); summarization (XL-Sum) is next.
- Latency measured with different precision and batch sizes across models.

**Q28. What would you do next?**
XL-Sum summarization with the same three-way design; error analysis of the 44 false abstentions;
ablations on rank and target modules; multiple seeds; a few-shot 7B baseline; then Phase 2 document tasks
(FUNSD, RVL-CDIP, DocVQA) with OCR input.

**Q29. Why does this matter in practice?**
A 0.5B model with a few-MB adapter, trained in 21 minutes on a free GPU, beat a 7B model on this task and
answered faster. One base model can host many small task adapters, which is far cheaper to deploy than a
large model per task.

## G. Reproducibility & engineering

**Q30. Can someone reproduce this?**
Yes: upload `notebooks/simple_pipeline.ipynb` to a Colab T4, set `DRY_RUN = False`, Run all. Seed 42,
saved test indices and greedy decoding make it repeatable — the base-model score matched exactly between
Colab and a local CPU run.

**Q31. What is `DRY_RUN` for?**
A ~5-minute run on 64 / 16 / 16 examples that exercises every cell (including the 7B) before committing
to the real run. Its scores are not results.

**Q32. Why is the notebook self-contained instead of importing `src/`?**
So it runs on Colab with nothing but the notebook file, and every step is readable in one place for
review. `src/` holds the same pipeline as a reusable library (`src/training/run_pilot.py`).
